## What Taskin is

Taskin is the layer between you and your work queue. It gives you one
vocabulary — create, start, pause, review, finish — and a set of tools on top of
it: a CLI, a real-time dashboard, an MCP server for AI agents, and metrics
derived from git history.

**Where the tasks are kept is your decision**, made once:

```bash
taskin init
```

```
? Choose a task provider
❯ 📁 File System   — markdown in a TASKS/ directory in your own repository
  🔴 Redmine       — issues over the REST API
  🔵 Jira          — issues over the REST API
  🐙 GitHub Issues — issues in the repository
```

The choice goes into `provider.type` in `.taskin.json`, and every command
respects it. A provider is a separate package installed on demand — you don't
carry the Jira client around to use local markdown, or the other way round.

::: info Where things stand
The **File System** provider is stable and is the default. Redmine, Jira and
GitHub Issues are listed in the `init` registry as `coming-soon`: the
architecture supports them and the contract is ready, but the packages haven't
been published yet.
:::

## The dashboard

`taskin dashboard` opens a panel that reads tasks from the configured provider
and follows changes over WebSocket — when someone runs `taskin finish` in the
terminal, or an agent calls `finish_task` over MCP, the card changes state
without a reload.

![Taskin dashboard showing six example tasks: three in progress, one blocked and two done. Each card shows number, status, title, project, a progress bar, estimated and spent hours, and the assignee. One of the in-progress tasks is assigned to "Claude (agente MCP)".](/dashboard.png)

The names there are examples — including the agent, which is listed as an
assignee on purpose: through the MCP server it picks up work from the same queue

## The contract that makes this work

A provider answers for six operations. That is all Taskin needs to know about
your backend:

```ts
interface ITaskProvider<TTask extends Task = Task> {
  initialize: () => Promise<void>;
  findTask: (taskId: TaskId) => Promise<TTask | undefined>;
  getAllTasks: () => Promise<TTask[]>;
  updateTask: (task: TTask) => Promise<void>;
  createTask: (options: CreateTaskOptions) => Promise<CreateTaskResult<TTask>>;
  lint: (fix?: boolean) => Promise<LintResult>;
}
```

The generic `TTask` is the detail that prevents leakage: the file system provider
adds `content` and `filePath` to a task, a Redmine one would add the `issueId`
and the note history, and none of that shows up in the agnostic package. Anyone
consuming plain `Task` keeps working with any provider.

`ITaskManager` sits on top with the state transitions — and is generic over the
same shape.

## The file provider, which is the default

If you don't use an issue tracker, or you want the task travelling alongside the
code, the File System provider keeps each one as markdown in your repository:

```markdown
# Task 042 — Status token contrast

Status: in-progress
Type: chore
Assignee: sidarta-veloso

## Description

The `--status-*-bg` tokens with white text fail WCAG AA.

## Tasks

- [x] Measure the contrast of each colour/text pair
- [ ] Decide between darkening the token or changing the text colour
```

Being a file in the repository, some things come for free: a change of scope
shows up in the PR diff, the task follows the branch where the work is, conflicts
are resolved with the tools you already use, and search is `grep`.

None of that is a Taskin requirement — it's what **this** provider offers. With
Jira, you trade those properties for the ones Jira gives you.

## For people writing code with an agent

The MCP server exposes the work queue as tools, and the agent that already reads
your repository starts acting on it:

```
you:    "finish task 042"
agent:  → finish_task(taskId: "042")
        → the task changes state, the commit goes out, the dashboard updates
```

The agent doesn't know — and doesn't need to know — whether that became an edited
file or a REST call. The provider settles that.

## The monorepo

| package | what it does |
| --- | --- |
| `taskin` | The CLI: `init`, `new`, `start`, `finish`, `lint`, `dashboard`, `mcp-server` |
| `@opentask/taskin-types` | Zod schemas and the domain types |
| `@opentask/taskin-task-manager` | The state transitions and the `ITaskProvider` contract |
| `@opentask/taskin-file-system-provider` | The default provider, in markdown |
| `@opentask/taskin-task-server-mcp` | The Model Context Protocol server |
| `@opentask/taskin-task-server-ws` | The WebSocket server behind real-time |
| `@opentask/taskin-dashboard` | The Vue 3 panel |
| `@opentask/taskin-design-vue` | The design system, and the mascot up there |
| `@opentask/ui-sense` | Sensor components: face, pose and gestures |

You can use just the CLI. Or just `task-manager`, with a provider of your own,
inside your own tool.
